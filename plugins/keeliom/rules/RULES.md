# Keeliom rules

The project formats, statuses and version rules. `CHECK.md` cites this file
and does not repeat it. A skill cites a section as `RULES.md §<heading>`.

## Project layout

```
<project>/
  app.md                # project overview
  STATUS.md             # generated by check; never edited by hand
  CLAUDE.md / AGENTS.md # each carries the Keeliom block
  changes/              # project history for app.md
  plans/                # optional human documents that span features
  features/
    F0001-add-book/
      brief.md          # optional; the raw request, saved once
      feature.md        # for people
      spec.md           # for agents and code
      changes/
        0001-initial.md
```

- A feature directory is `F<4 digits>-<slug>`.
- A project does not keep the rules files. The plugin owns them.
- `brief.md` is the raw request. It is saved once and never edited.
- `STATUS.md` is generated by `check`. Never edit it.
- `plans/` is optional. Keeliom prescribes no sections for a plan.

## Language

- `app.md` sets `Language:`. The default is `English`.
- `feature.md`, `spec.md`, `changes/` and `plans/` are written in that
  language.
- `brief.md` stays in the language it arrived in.
- Headings, header keys, IDs and code identifiers are English. Never translate
  them.

## Plans

- A plan is a free-form human document that spans features: a redesign, a
  release, a phase.
- `plans/<file>.md §<section>` is a valid `Source` for a Decision and for a
  change entry.
- A plan is a proposal and a record of reasoning. Once its content lands in
  features, `feature.md` and `spec.md` are the current truth.
- Plans are not kept in sync with features.

## app.md

```markdown
# Book Library

Keeliom: 0.4.0
Status: ready
Language: English
```

- `Status` is `draft` or `ready`.
- Required sections, in this order: `One-liner`, `Users`, `Scope`,
  `Non-goals`, `Glossary`, `Invariants`, `Stack`, `Roles`, `Data model`.
- `Users` is a table `| User | Description |`. Users are the people the app
  serves.
- `Roles` is a table `| Role | Can do |`. Roles are access roles only.
- `Data model` is a table `| Entity | Owner | Key fields | Notes |`. `Owner`
  is the feature ID that owns the entity.
- `Repositories` is required when the project has code. It is a table
  `| Path | Role | Language | Test commands | Notes |`.
- Optional sections: `Conventions` (free text), `Locales`, `Accessibility`,
  `Check overrides`.
- `Check overrides` is a bullet list. Each bullet names a check ID and the
  reason. `check` applies them and prints each applied override.

## feature.md

For developers and product owners. It must be understandable without
`spec.md`.

```markdown
# F0001 — Add book

Status: ready
Source: brief.md

## Overview

A reader records a book they own so it appears in their library.

## Description

### Adding a book

The reader enters a title, an author and, optionally, an ISBN.

## Out of scope

- Editing an existing book (F0003).

## Decisions

| ID | Decision | Source | Status |
|---|---|---|---|
| D1 | Title and author are trimmed before saving. | owner:ana, 2026-10-30 | approved |

## Open questions

- Q4. Should a duplicate title by the same author be allowed?
  Recommendation: yes, with a warning. Owner: ana.
```

- Header lines: `Status`, `Source`, and `Replaced by: F00xx` when the feature
  is deprecated.
- `Source` is a ticket ID, a URL, `brief.md`, `plans/<file>.md`, or
  `code:<path>`.
- Required sections: `Overview`, `Description`, `Out of scope`, `Decisions`,
  `Open questions`.
- `Overview` is a short paragraph: what the feature does and why.
- `Description` describes what the user experiences, in subsections by topic.
  Values the owner stated, such as prices and limits, may appear here. Error
  codes, HTTP statuses, field types and routes go in `spec.md`. An ASCII
  sketch of a screen is allowed.
- `Out of scope` is a bullet list. Name the owning feature when one exists.
- `Decisions` is a table with the header `| ID | Decision | Source | Status |`.
  - IDs are `D<n>` and are never reused.
  - `Status` is `approved`, `assumed`, or `replaced by D<n>`.
  - A replaced row stays in the table.
  - A decision never cites its own feature's `spec.md` as its source.
  - `assumed` marks a choice the owner has not confirmed.
- `Open questions` uses `- Q<n>. <question>` followed by indented
  `Recommendation: … Owner: …` lines.
  - Question numbers are never reused.
  - When a question is answered, remove it and add a Decision. The change
    entry records the answer.
  - When the owner overrode the recommendation, the entry's `Reason` says
    `recommended: <x>`.
- An empty `Decisions` or `Open questions` section contains `None`.
- `feature.md` carries no check grammar: no check IDs and no line references.

## spec.md

For agents and code. It adds precision to `feature.md`.

```markdown
# F0001 — Add book — spec

Depends on: F0003
Repositories: None

## Rules

- R1. `title`: required, trimmed, 1–120 chars. Error `title_required` → 422. (§Adding a book, D1)
- R4. `POST /books` returns 201 with the saved book. (§Adding a book)

## Data

- Book: id, title, author, isbn.

## API

- `POST /books`

## Tasks

- [ ] In api: add the `books` table.
```

- Header lines: `Depends on`, and `Repositories` when `app.md` lists more
  than one repository.
- `Depends on` lists feature IDs or `None`. It merges behavior, data and
  relation references from v0.3. Cycles are allowed.
- Required section: `Rules`.
- Optional sections: `Data`, `API`, `Screens`, `Tasks`. Omit an empty one or
  write `None`.
- A rule is `- R<n>. <text>`. IDs are stable and never reused. A removed rule
  retires its number.
- Every rule ends with a reference to a `feature.md` `Description` subsection
  `(§<heading>)`, a Decision `(D<n>)`, or both `(§<heading>, D<n>)`.
- A rule is testable: it names an observable output, a value with a unit, or a
  `test:<name>`.
- `spec.md` does not restate a requirement without adding a technical detail.
- Other features, plans and notes cite a rule as `F00xx R<n>`.
- `Tasks` holds optional checkboxes. `In <repo>:` marks a task for one
  repository. When `Tasks` exist, `done` requires every box ticked.
- A behavior change comes from a `feature.md` change or a Decision. A pure
  refinement, such as an error code or a field type, needs no change entry.

## Change entries

```markdown
# 0004 — Duplicate ISBNs are rejected

- Date: 2026-11-07
- Reason: The owner chose to reject duplicate ISBNs (recommended: warn only).
- Changed: Q2 answered; a duplicate ISBN blocks saving.
- Decisions: D4
- Source: owner:ana, 2026-11-07
```

- Five fields, with these keys: `Date`, `Reason`, `Changed`, `Decisions`,
  `Source`.
- `Decisions` lists IDs or `None`.
- Write an entry when a requirement or a decision changes: any `feature.md`
  change other than `Status`, or a `spec.md` behavior change.
- Write no entry for spec maintenance: review fixes, wording, format
  migrations, rule renumbering. Those go in the git commit message.
- Entries are append-only. To correct one, add an entry whose `Reason` names
  the corrected entry number.
- Files are `NNNN-<slug>.md`, sequential, never reused.
- Project-level entries for `app.md` use the same format.
- Every Decision ID appears in at least one entry, or in the project migration
  entry.

## Statuses

| From | To | Condition |
|---|---|---|
| `draft` | `ready` | No `TBD`. No open questions. Every Decision `approved` or replaced. `app.md` is `ready`. `check` has no errors for the feature. |
| `ready` | `done` | The code implements the rules. Tests pass when a test command exists. `Tasks`, if any, are all ticked. `check` has no errors. |
| `ready`, `done` | `draft` | A requirement changed and the spec needs work. Add a change entry. |
| any | `deprecated` | `Replaced by: F00xx` is set. |

- `draft` is the starting status.
- A status change alone needs no change entry.
- Ticket systems track who works on what. Keeliom does not.

## Version

- The plugin version is the source of truth. A project records it as
  `Keeliom: <version>` in `app.md`.
- Compare the major and minor parts. Ignore the patch.
- A project with `KEELIOM_VERSION` and no `Keeliom:` header counts as older.
- Project older: run, then print `Migration required: run the migrate skill.`
- Project newer: print `Plugin is older than the project: update the keeliom
  plugin.` and stop.

## Project instructions

- `setup` and `migrate` write one block into the project's `CLAUDE.md` and
  `AGENTS.md`. They create a file when it is missing.
- The block tells the agent to read `app.md`, then the feature's `feature.md`
  and `spec.md`; to implement `spec.md`; to stop and ask when code and spec
  disagree; to add a change entry when a requirement changes; to run `check`
  before setting `done`; and where the rules live.
- The block sits between `<!-- keeliom:start -->` and `<!-- keeliom:end -->`.
  The template holds its text.
- Outside the markers the file belongs to the project. Never edit it.
